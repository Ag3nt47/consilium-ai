# Signal & Cross-Workstation Messaging Integration Specification

This specification documents the architecture for bridging Signal and a future companion-app transport into local Consilium instances across multiple workstations (macOS, Windows, Linux).

---

## 1. Core Requirements & Privacy Guardrails

1. **Zero Credential & Contact Leakage:**
   - Phone numbers, Signal registration IDs, ACI/UUID values, API tokens, and local socket credentials must **never** be checked into git, logged in plain text, or included in shared transcripts.
   - All connection metadata resides in local OS keychain or `~/.config/consilium/messaging.json` (mode `0600` on Unix), protected by Consilium’s `check-secrets` pre-commit gate.
2. **Multi-Workstation Hub (Mac & Windows):**
   - When the user sends a message via Signal from their mobile device, it is accepted only when its Signal ACI/UUID matches the local allowlist, then dispatched to registered workstation nodes.
   - Responses generated by the council are formatted concisely and relayed back to the mobile client.
3. **Offline / Bluetooth Fallback (Separate Companion App):**
   - Signal does not transport messages over a custom BLE service. Offline BLE therefore requires a separate Consilium mobile companion app; it is not part of the first Signal bridge.
   - The companion transport uses OS pairing plus application-level authenticated encryption and replay protection before it can relay text to a nearby workstation.

## 2. Architectural Components

```
                      +-----------------------------+
                      | Mobile Device: Signal app  |
                      | or future companion app    |
                      +--------------+--------------+
                                     |
                    (Signal network / companion BLE)
                                     |
               +---------------------+---------------------+
               |                                           |
    +----------v----------+                     +----------v----------+
    | Workstation 1 (Mac) |                     | Workstation 2 (Win) |
    |   Consilium Core    |                     |   Consilium Core    |
    | [signal-cli daemon] |                     | [signal-cli daemon] |
    +----------+----------+                     +----------+----------+
               |                                           |
               +------------------- P2P -------------------+
                             (Sync Mesh)
```

### Component A: Signal Bridge Adapter (`signal-cli` / Socket Mode)
- **Local Daemon:** Uses a local `signal-cli` daemon connection bound to loopback or a local socket. It is never exposed directly to the LAN or internet.
- **Message Ingestion:** Incoming messages from allowlisted sender ACI/UUID values are ingested as `[Human] <message>` in the active conversation turn. Events are deduplicated by sender, source device and message timestamp before dispatch.
- **Outbound Stream:** Council consensus summaries (or red `REQUEST:` lines) are sent back to the verified recipient.

### Component B: Cross-Instance Synchronization
- **State Relay:** Each running Consilium workstation broadcasts a cryptographic heartbeat over the local subnet (or Tailscale/WireGuard mesh).
- **Leader Election:** When multiple workstations are active, one node coordinates turns while the other maintains synchronized mirror state, preventing duplicate responses.

### Component C: Offline Bluetooth Low Energy (BLE) Companion Transport
- A future Consilium mobile companion app, not the Signal app, connects to a nearby workstation through a platform-valid 128-bit GATT service UUID.
- OS Bluetooth pairing alone is not the authorization boundary. The companion and workstation also authenticate each other, encrypt payloads and reject expired or replayed messages.
