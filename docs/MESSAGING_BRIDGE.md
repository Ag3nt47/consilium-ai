# Signal & Cross-Workstation Messaging Integration Specification

This specification documents the architecture for bridging Signal and a future companion-app transport into local Consilium instances across multiple workstations (macOS, Windows, Linux).

---

## 1. Core Requirements & Privacy Guardrails

1. **Zero Credential & Contact Leakage:**
   - Phone numbers, Signal registration IDs, ACI/UUID values, API tokens, and local socket credentials must **never** be checked into git, logged in plain text, or included in shared transcripts.
   - All connection metadata resides in local OS keychain or `~/.config/consilium/messaging.json` (mode `0600` on Unix), protected by Consilium’s `check-secrets` pre-commit gate.
2. **Multi-Workstation Hub (Mac & Windows):**
   - When the user sends a message via Signal from their mobile device, it is accepted only when its Signal ACI/UUID matches the local allowlist, then dispatched to registered workstation nodes.
   - Responses generated by the council are formatted concisely and relayed back to the mobile client.
3. **Offline / Bluetooth Fallback (Separate Companion App):**
   - Signal does not transport messages over a custom BLE service. Offline BLE therefore requires a separate Consilium mobile companion app; it is not part of the first Signal bridge.
   - The companion transport uses OS pairing plus application-level authenticated encryption and replay protection before it can relay text to a nearby workstation.

---

## 2. Architectural Components

```
                      +-----------------------------+
                      | Mobile Device: Signal app  |
                      | or future companion app    |
                      +--------------+--------------+
                                     |
                    (Signal network / companion BLE)
                                     |
               +---------------------+---------------------+
               |                                           |
    +----------v----------+                     +----------v----------+
    | Workstation 1 (Mac) |                     | Workstation 2 (Win) |
    |   Consilium Core    |                     |   Consilium Core    |
    | [signal-cli daemon] |                     | [signal-cli daemon] |
    +----------+----------+                     +----------+----------+
               |                                           |
               +------------------- P2P -------------------+
                             (Sync Mesh)
```

### Component A: Signal Bridge Adapter (`signal-cli` / Socket Mode)
- **Local Daemon:** Uses a local `signal-cli` daemon connection bound to loopback or a local socket. It is never exposed directly to the LAN or internet.
- **Message Ingestion:** Incoming messages from allowlisted sender ACI/UUID values are ingested as `[Human] <message>` in the active conversation turn. Events are deduplicated by sender, source device and message timestamp before dispatch.
- **Outbound Stream:** Council consensus summaries (or red `REQUEST:` lines) are sent back to the verified recipient.

### Component B: Cross-Instance Synchronization
- **State Relay:** Each running Consilium workstation broadcasts a cryptographic heartbeat over the local subnet (or Tailscale/WireGuard mesh).
- **Leader Election:** When multiple workstations are active, one node coordinates turns while the other maintains synchronized mirror state, preventing duplicate responses.

### Component C: Offline Bluetooth Low Energy (BLE) Companion Transport
- A future Consilium mobile companion app, not the Signal app, connects to a nearby workstation through a platform-valid 128-bit GATT service UUID.
- OS Bluetooth pairing alone is not the authorization boundary. The companion and workstation also authenticate each other, encrypt payloads and reject expired or replayed messages.

## 4. Consilium Watchdog on Windows

With Signal verified and enabled, run `consilium watchdog-signal setup` once from the installed Windows app's terminal command. It creates or verifies the private **Consilium Watchdog** group and starts a hidden listener that can stay running when the app closes. Consilium starts the listener again when it opens in a new Windows session.

From the primary Signal phone, send one of these messages in **Consilium Watchdog**.

- `status` checks whether the watchdog can see the Windows app.
- `restart` opens the app or restarts it if it is running.
- `restart signal` asks the Windows app to reconnect its Signal listener. If the app is closed, use `restart`.

The watchdog accepts only these commands from the verified primary phone in the private group. It uses the existing linked Signal account and needs Signal service connectivity. If the local daemon stops, the watchdog can start it with the saved registration. It can replace an unresponsive daemon only when it owns that process.

While the desktop is unavailable, the listener can save up to 64 ordinary Consilium group messages locally for 15 minutes. Verification, approval, and launcher commands need the live desktop conversation.

App relaunch attempts are recorded in `watchdog/relaunch.log` inside the Consilium data folder. The helper confirms its own startup before the app exits, then waits for the original process before reopening the app.

## 5. Scheduled Windows wake and network power commands

On Windows, `scripts/Install-ConsiliumWakeTimer.ps1` registers an hourly wake task on AC power while the current user stays signed in. The first run is one hour after installation. The task gives the running Signal listener one minute to reconnect, with the display free to stay off. Windows handles unattended return to sleep. Run the script with `-Action Inspect` to see its schedule or `-Action Disable` to pause it. The active power plan must allow wake timers on AC.

Run `node scripts/watchdog-commands.mjs` with the updated installed app to post the command list and timing to **Consilium Watchdog**. `consilium watchdog-signal commands` sends the same list.

The listener can accept an explicit `wake mac` or `wake linux` after Windows resumes. A wake request can wait up to two hours for the next check. Sleep requests expire after one minute. The normal Windows desktop commands keep their five-minute limit, so send them when Windows is awake.

To handle network power commands, verify Signal on the relay and run `consilium watchdog-signal relay` with a local `watchdog-power.json` in its Consilium data folder. The relay can run on the Windows PC during the hourly check, or on a separate device that stays awake. Private group membership and the primary phone are checked before an operation runs.

Configure only the computers you intend to control. For example, a Windows relay with a Mac as its sole target can use a file like this after replacing the addresses and SSH settings.

```json
{
  "ssh_config": "C:/Users/you/.ssh/consilium-watchdog",
  "mac": {
    "wake": {
      "mac": "02:11:22:33:44:55",
      "source_ipv4": "192.168.10.20"
    },
    "ssh_alias": "consilium-mac",
    "status_endpoint": "192.168.10.21:22"
  }
}
```

`source_ipv4` is the relay's local address on the target's network. The corresponding adapter supplies the local broadcast address. Use the target's wake-capable Ethernet MAC address and test each machine from actual sleep. `power status` shows which configured TCP endpoints accept a connection.

Sleep requires working public-key SSH with the host key already verified and an account permitted to suspend that PC. Limit the relay's SSH key to the fixed `consilium watchdog-signal sleep-local` command. Test individual targets and their wake paths before using `sleep both`. The `both` commands require a Windows target and one Mac or Linux target.
